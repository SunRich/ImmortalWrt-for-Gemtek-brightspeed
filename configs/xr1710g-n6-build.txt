Fixes:
  - Notify NPU when a non-MLO station is finally removed, before WCID reuse.
    This remains a candidate cause-specific fix pending controlled device tests.
  - Do not force log-facility=/dev/null from a first-boot script.
    Explicit UCI logging takes precedence over a duplicate static directive.
    Raw-only settings and existing comments are preserved; application is
    idempotent. The initializer does not edit UCI or restart dnsmasq.
  - Retain the boot-proven legacy partition map, I2C compatible and WAN reset.
  - Pin feeds and the generated SDK base feed to immutable commits.

Cloud workflow: .github/workflows/xr1710g-n6-stability.yml
  Push to codex/xr1710g-n6-stability or dispatch manually.
  Build only gemtek_xr1710g, with the matching SDK and binary package set.
  Source and image verification reject known package regressions, the wrong
  profile, invalid FIT payload hashes, an unexpected device tree, unexpected
  NPU firmware, missing fix code, or kernel overlap with reserved NPU memory.
  Successful outputs are published as a prerelease in the fork, including
  manifests, effective configuration, provenance and SHA256SUMS.

Local checks:
  bash scripts/test-dnsmasq-logfacility.sh   (requires dnsmasq; syntax only)
  bash scripts/setup-xr1710g-n6.sh           (Linux, installs pinned feeds)
  python3 scripts/verify-xr1710g-n6.py source

Cloud validation is not hardware acceptance. No workflow flashes a device.
After separate upgrade authorization, verify first boot, actual DHCP exchange,
repeated service reload, client reconnection/WCID reuse and sustained transfer.
Do not infer hardware stability solely from a successful build or transfer.
Only the legacy gemtek,xr1710g layout is targeted; UBI migration is separate.
